## Critical Gaps

### 1. Broken Error Handling Endpoints (Production Risk)

Both error-handling middleware references point to non-existent endpoints:

- **`UseExceptionHandler("/Error")`** — `Program.cs:136`, no `/Error` route exists (no controller, no `MapGet`, no Razor page)
- **`UseStatusCodePagesWithReExecute("/not-found")`** — `Program.cs:144`, no `/not-found` server endpoint exists; client-side Blazor handles `/notfound` only

**Impact:** In production, any unhandled exception or 404 produces undefined behavior (infinite redirect loop or blank response). This affects:

- Unhandled exceptions from services that omit try/catch
- FluentValidation model validation failures (HTTP 400 → re-execution to `/not-found` → failure)
- `AuthorizeSessionAttribute` returning `ForbidResult()` (HTTP 403 → same loop)

**What is documented:** Tech doc covers Result pattern for control flow and per-service try/catch patterns.

**Missing:** Middleware-level error handling strategy, the broken endpoints, and HTTP status code semantics.

### 2. No Deployment/Packaging Documentation

The SPK packaging pipeline is a multi-phase process entirely undocumented in `technical-architecture.md`:

**Build Pipeline** (`src/scripts/build-spk.sh`):

1. Pre-flight checks: verifies `curl`, `tar`, `dotnet`, `jq`, `awk`, `pigz` availability
2. .NET runtime download: reads `ChannelVersion` from `appsettings.json`, fetches Microsoft releases metadata, downloads aspnetcore-runtime for `linux-arm`, `linux-arm64`, `linux-x64` with SHA512 verification
3. Application publish: Framework-dependent (`--self-contained false`) to `spk-project/package/admin-ui/`
4. SPK assembly: compresses via `pigz -2`, creates tar archive containing `INFO`, `package.tgz`, lifecycle scripts, configuration, icons

**SPK Metadata** (`src/spk-project/INFO`):

- Package identifier: `AskylWebHosting`, version `0.6.0`, DSM minimum `7.2-64561`
- Port conflict detection on `7120`, beta + third-party flags, silent install/upgrade/uninstall

**Lifecycle Scripts** (`src/spk-project/scripts/`):

| Script | Purpose |
|--------|---------|
| `preinst` / `postinst` | Environment setup, .NET runtime installation for detected architecture |
| `preupgrade` / `postupgrade` | Service stop, config backup/restore, runtime reinstall |
| `preuninst` / `postuninst` | Service stop, PID cleanup |
| `start-stop-status` | Service lifecycle with PID management |
| `common-functions.sh` | Shared utilities: logging, process management, runtime install/verify |

**Nginx Integration:** `adwh-alias.conf` provides reverse proxy from `/adwh` → `localhost:7120`, injected via DSM's `web-config` resource declaration.

**Service Account:** Dedicated system user `AskylWebHosting` in `http` group (`conf/privilege`).

**Version Management:** Dual sources of truth — `Directory.Build.props` (.NET assembly) and `spk-project/INFO` (SPK package), synchronized manually via `scripts/update-version.sh`.

**Missing from documentation:**

- Complete build pipeline from code to SPK
- Runtime selection strategy at install time (fat package, thin extract per architecture)
- Nginx reverse proxy integration mechanism
- Service account and permissions model
- Data persistence paths (`/var/packages/AskylWebHosting/var/`)
- Port configuration flow (`adwh.sc`: HTTP 7120, HTTPS 7121)

### 3. No CI/CD Pipeline

**Current state:** Entirely manual workflow:

1. Developer runs `build-spk.sh` locally
2. Resulting `.spk` copied from `dist/` to target NAS via Package Center

**Missing:**

- Automated build on commit or PR
- Automated test execution before packaging
- SPK lifecycle script testing (install/upgrade/uninstall against DSM)
- Release notes or changelog automation
- Versioned artifact storage and distribution
- Code signing (no `.pfx` certificates, no Synology package signing)

## Significant Gaps

### 4. Test Strategy: Partial Coverage With Anti-Patterns

**What exists:** ~42 test files across Globalization, Data domain models, Results, Analyzers, UI services, and Tools infrastructure. Framework: xUnit + Moq + coverlet.

**Framework discrepancy:** Tech doc (line 80) states "xUnit, Moq, **FluentAssertions**" but FluentAssertions is absent from `csproj`. All assertions use xUnit `Assert.*` directly.

Similarly, `bunit` (v2.7.2) is referenced but only used for `BunitContext` in `AuthenticationNavigationGuardTests.cs` — zero Blazor component tests exist.

**Services with zero test coverage:**

| Service/Component | Location | Risk |
|-------------------|----------|------|
| All 6 API Controllers | `Ui.Controllers/` | API contract changes undetected |
| `AuthorizeSessionAttribute` | `Ui.Authorization/` | Auth filter untested |
| `PlatformInfoService` | `Tools.Infrastructure` | Platform detection logic |
| `DownloaderService` | `Tools.Runtime` | HTTP download, cancellation paths |
| `SystemProcessRunner` | `Tools.Infrastructure` | Process spawning (faked in SLM tests only) |
| All Ui.Client HTTP proxies | `Ui.Client.Services/` (10 services) | Client-server contract drift |
| FluentValidation validators | `Globalization.Validators/` | Validation rule regression |

**Integration test coverage:** None. Every test mocks all dependencies. Missing: controller → service integration, real HTTP calls to DSM API, Blazor component rendering, configuration persistence end-to-end.

**Anti-patterns observed:**

- `[Collection("WebSiteHostingService")]` without matching `[CollectionDefinition]` — no effect
- Temp directory leak in `WebSiteHostingServiceTests` (creates `_tempDir`, never cleans up)
- Magic string assertions couple tests to localization strings rather than structured result properties
- No test data factories — repetitive inline object construction across all test files

### 5. Configuration Management: Undocumented Structure

**Server appsettings.json** (`Ui/appsettings.json`):

```json
{
  "Download": { "ChannelVersion": "10.0" },
  "Serilog": { /* file sink, rolling daily, 10MB limit, 7-day retention */ },
  "AllowedHosts": "*"
}
```

**Client appsettings.json** (`Ui.Client/wwwroot/appsettings.json`):

- BrowserConsole Serilog sink with Debug minimum level for `Askyl.Dsm` namespace

**Dual-purpose configuration:** `Download.ChannelVersion` serves two roles:

1. Build-time: `build-spk.sh` reads it to determine which .NET runtime to download
2. Runtime: Application uses it for version detection and release fetching

This coupling is undocumented and represents a constraint on deployment independence.

**IOptions pattern:** Not used anywhere in the codebase. Configuration accessed via `builder.Configuration[]` directly or through dedicated services (`DsmSettingsService` reads `/etc/synoinfo.conf`).

## Minor Gaps

### 6. Performance Metrics: No Targets Defined

Tech doc documents caching strategy (ApiInformations lazy-init, session validation 1-minute TTL, instance cache). Missing:

- Response time targets for API endpoints
- Memory usage guidelines for long-running hosting service
- Connection pool sizing rationale for `HttpClient` instances
- Load testing results or capacity planning data

### 7. Error Correlation: No Request Tracing

No request ID or trace ID propagation across the UI → API controller → service → DSM API call chain.

Serilog's `WithActivity` enricher adds `ActivityId`, `ActivityTraceId`, and `ActivitySpanId`, but these are not surfaced to clients for support ticket correlation.

### 8. Dead Code: Unused Exception Type

`MandatorySettingMissingException` is defined in `Data/Exceptions/` but never thrown anywhere in the codebase.
